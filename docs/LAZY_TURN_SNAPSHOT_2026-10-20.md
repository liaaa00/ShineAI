# 将文件快照移到工具执行前

本次替代“每次发送前等待三秒快照”的方案。原先加在 `captureSnapshot` 前的 `await`
是发送延迟的回归来源；上一轮预算限制只是缩短了它，没有移除发送前的 Git 等待。

## 行为

- 每次实际派发用户消息时，仅写入本轮的不可用基准记录，不启动 Git。包含排队后派发的
  用户消息，跳过内部会话与 `agent_completion`，不改变它们的队列、权限或输入语义。
- API 原生工具执行器、Claude SDK 的 PreToolUse 在首个可能修改文件的工具前捕获基准。
  常见的明确只读工具直接运行；shell、未知 MCP、委派工具保守等待基准准备。
- 同一轮并行工具共享一个捕获；其子进程结束后才能执行工具。保留三秒预算、独立 index、
  超时取消与失败冷却。失败仍可继续原有工具执行，但明确没有该轮文件恢复能力。
- 原始快照行保留发送前的时间，收到用户消息后绑定消息 ID，捕获完成更新同一行。
  不能简单地在写工具前追加一条晚于用户消息的快照，否则撤销定位可能落到旧快照。
- 新轮次使旧捕获失效并请求终止真实子进程。旧工具在等待结束后检查取消，不继续写文件，
  旧捕获也不能把成功提交写回已失效的基准。
- 不具备可靠执行前拦截的外部 CLI（包括当前 Codex 入口）不运行自动文件快照；
  保留对话撤销，文件撤销预览返回不可用。这是明确的能力限制，不能声称这些入口有
  安全文件快照，也不将其异步捕获的目录状态伪装成修改前基准。

## 验证设计

- 真实原生工具执行方法验证：发送/明确只读不捕获；并行写入前只捕获一次；
  捕获未结束文件不变；失败基准、取消、新轮次、SDK 权限决定均保持正确。
- 真实派发选项方法验证用户派发建立基准，内部完成不覆盖现有轮次。
- 实际 SQLite 和 Git 验证延迟捕获保留发送边界、绑定真实消息 ID、恢复用户未提交编辑，
  以及外部 CLI 不在重启后错误继承旧成功基准。
- GUI 使用实际项目目录、独立配置与本地固定 HTTP 模型验证普通聊天完全不启动快照，
  首次请求与连续请求计时，以及立即显示、滚动、去重、失败保留草稿与明确重试。

实际服务商网络、首包与推理耗时不属于本地发送测试结论。
