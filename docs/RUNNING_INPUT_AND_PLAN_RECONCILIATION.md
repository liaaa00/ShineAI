## 目标

用户在任务执行期间发送补充、纠正或新要求时，消息进入后续模型请求的状态可见；
模型继续执行前须结合最新要求核对旧计划。停止按钮不再覆盖任务看板。

看板保留。新消息不自动取消所有旧任务，也不自动把未完成事项标成完成。
普通消息不强行中止已经开始的命令；已开始的文件操作不会因新消息自动回滚。

## 1. 先建立消息投递状态

- 顺着 SessionManager、适配器 pendingMessages、AgentLoop 的输入边界确认真实生命周期。
- 为运行中消息关联稳定 ID，区分“排队中”“已加入模型请求”“投递失败”。
- 适配器接收或管理器移出队列不能视为模型请求已包含消息。
- UI 不显示无法证实的“模型已读”。支持情况不同的适配器分别标明能力。
- 处理发送失败、取消、自动压缩、恢复会话及附件路径；保留可重试的输入，避免重复注入。

验收：用本地模型模拟服务核对实际请求中的消息 ID 对应内容及顺序；界面状态与请求一致。

## 2. 最新要求参与下一轮执行决策

- 在适配器允许的输入节点加入用户消息，并明确用户最新要求用于调整当前执行方向。
- 遵守系统指令与原有权限约束，历史计划不能高于用户后续纠正。
- 提醒模型在继续工具操作前核对旧计划，必要时修改任务、暂停过时任务或说明冲突。
- 保留补充说明的语义，不把每条消息当成更换整个目标，也不自行取消无关任务。
- 同批多个新消息保持到达顺序；模型正常结束、等待权限或等待用户时另行处理队列，避免饿死。
- 明确区分原生 API 可控循环与 Claude/Codex SDK 的输入机制，不宣称所有适配器都能即时打断。

验收：模拟服务证明下一次请求包含最新要求及计划核对指令；实际模型是否遵循需单独观察，
不能用固定模拟响应证明模型一定会改变执行方向。

## 3. 给旧看板增加修订状态

- 绑定计划版本与用户输入序号，记录计划对应到哪一次已投递输入。
- 有更新输入送入请求后，旧计划标记“待核对”，不再让旧进度看起来代表最新要求。
- 接受模型明确的核对或计划更新后，恢复正常展示；没有计划变化也应允许明确确认继续。
- 取消与完成分开表达。新增状态通过可读扩展或独立元数据实现，兼容旧会话与工具格式。
- 不把 UI 清空当作计划已修订，不让过期更新覆盖更新版本；检查完成事件的自动标完成逻辑。

验收：原有 pending/in_progress/completed 正常展示；更正、补充、取消部分任务、连续输入、
延迟到达的旧计划更新以及重启恢复均保持一致，不出现自动全完成。

## 4. 修复停止按钮布局

- 在输入区域安排独立操作位置，让停止按钮参与布局且保持可点击。
- 检查看板展开/收起、本轮记录、长任务文本、小窗口、缩放及跳到最新按钮之间的关系。
- 沿用当前字体、主题与全透壁纸，不附加背景遮罩。

验收：不同窗口尺寸和面板组合中无按钮覆盖、文本重叠或点击阻挡；停止功能保持原有语义。
