## 程序中的恢复优先级问题

主进程函数 `cW` 拼接恢复提示时加入：

> Layer 0: Original User Task (verbatim, authoritative)
>
> The goal, scope and prohibitions above come from the user and override anything below that drifted.

函数 `uW` 从最早用户消息取得原始需求。这会把长会话最初的服务器问题放在后续画布任务之前，并赋予可覆盖后文的地位。当前数据库保存的恢复提示也包含上述两句，原始需求中包含服务器 IP。它是实际存在的上下文优先级缺陷。

注意：当前恢复提示已经在后续重启中重建，不是错误回答时完整网络请求的留档，因此不能据此断言模型当时每一条输入具体是什么。

## 最近选项可能被截掉，已按原生函数复现

恢复函数 `rW` 对每条助手回复调用 `UH(text, 320)`，保留开头而不专门保留结尾的问题或选项。将消息 6527 的实际文本交给同一原生截断函数：1957 字符被裁到 857 字符，末尾“保持现状”和“文字区拖=选字”的选项均消失。这会使下一条四字回复失去它对应的问题，同时最初的服务器需求仍在恢复提示首层。

这是当前恢复算法可稳定复现的缺陷；不是错误发生时网络请求的直接留档。复现结果在 `artifacts/context-memory-audit/recovery-excerpt-report.json`。

## “只拿到迁移前摘要”的自我解释不准确

错误回答前最近的 `compact_summary`（815，21:58:04）明确讨论画布拖拽、吸附、框选等改造；`rolling_summary`（818，22:10:49）也是画布交互内容。它们没有部署完成信息，但同样不是助手所称的“只保留迁移前服务器需求”。

完整聊天记录仍保存在本地数据库，并不等于这些记录全部进入了某一次模型请求。助手将推测写成了确定的故障原因。

另外，rolling_summary 818 与后续 823 的内容完全相同，虽然后续已经发生纠正；摘要新建时间不能单独证明内容已追上最新进展。上下文压缩验证记录为 `unknown / provider_unavailable`，没有证明压缩后保留了所有关键事实。

## 长期记忆拒绝已复现

四次 `memory_save` 的实际工具结果均为 `action: rejected`，却同时返回 `ok: true` 和通用错误文案。

从本项目原生代码中提取校验函数，在独立 VM 内只读复现：

| 6560，195 字项目事实与核对规则 | `mutable_world_state` |
| 6562，87 字“先查再答”的长期规则 | `mutable_world_state` |
| 6564，50 字“先查再答”的长期规则 | `mutable_world_state` |

`UP` 中的正则 `/(部署|发版|上线|发布)\s*(到|了|完成|成功|失败|状态)?/` 后半部分为可选，导致只要出现“部署”就命中。它不区分临时部署状态与长期操作原则。

对同一条长期规则，仅去掉“与部署状态”五字，校验即通过。这证实存在误拦截，不是记忆服务不可连接。

复现：`node artifacts/context-memory-audit/reproduce-validator.mjs`。结果：`artifacts/context-memory-audit/validator-report.json`。复现不向实际记忆库写入内容。

`memory_recall` 当时返回 0 个匹配候选，只能证明该查询没有召回候选，不能证明整个长期记忆库没有任何记录。

## 修复方向

1. 原始需求保留为历史背景；最新用户要求、最近明确选项与后续纠正优先，不能默认将后续话题当作偏离。
2. 对“保持现状／可以／第一个”等短回复，保留并优先绑定紧邻的问题、选项及答复。
3. 摘要携带明确来源、覆盖消息范围和更新时间；对已完成事项更新状态，避免旧总结以新时间反复保存。
4. 记忆校验区分长期原则与易变状态，给出准确拒绝原因和可执行建议。实时部署位置以项目运维记录和当次核验为准。
5. 服务状态断言应基于文件或实测证据，模型没有请求留档时不得自行认定“摘要丢失”就是唯一原因。
