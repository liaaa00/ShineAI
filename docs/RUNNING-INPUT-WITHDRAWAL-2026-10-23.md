# 运行中输入的撤回

此次修复连接运行中输入状态栏与实际消息队列。撤回成功的依据是同步移除了仍在本地持有的原消息，不是删除界面上的文字，也不是收到 SDK 的 sendMessage 返回值。

## 行为

- 本地排队的文本消息显示“撤回”；点击后重新核对队列，移除该消息并恢复原文到输入框。
- 输入框已有草稿时，将撤回原文追加到草稿后，不覆盖已有文字，也不自动发送。
- 当前模型任务继续执行，其他消息保持原顺序。
- 已有实际请求记录的消息拒绝撤回；连接层已取走、无法确认实际发送状态的消息显示“无法保证撤回”。
- “等待投递确认”改为“已交给连接层，发送状态未确认”，避免误认为消息尚在本地排队。
- 原队列列表的删除按钮和清空队列复用同一判断，不把已交出的消息标成撤回成功。
- 撤回同步移除即时消息预览及旧的绿色排队提示，以输入 UUID 区分同文消息，避免成功撤回后界面仍显示排队。

## 支持边界

检查会话管理器的启动、运行中和回合后队列，原生 API 的 pendingMessages，Codex 的 delayedInputQueue，以及 Claude SDK 输入迭代器仍未消费的 queue。移除过程不包含 await，因此不会在检查和移除之间插入一次队列消费。

消息以输入 UUID 和版本精确定位。仅接受能确认属于单条输入的文本；合并后的恢复提示、未知格式、带独立图像块的 SDK 输入保守拒绝撤回。已交给 SDK 的待处理 resolver 或已经进入请求的消息无法追回。停止生成也不等于撤回。

Claude SDK 可能先生成本地聊天记录，再由迭代器消费输入。成功撤回后，从运行时记录及后续数据库读取结果中排除该输入，原始数据库记录保留作审计。独立保存撤回的 UUID，避免超过最近 40 条输入后又参与恢复。异步投递随后报错也不能把撤回状态改回“可重试”。
